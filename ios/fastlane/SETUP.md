# Shipping TotoApp: the automated path

This replaces the manual "Product → Archive → click through Xcode"
flow in `../DEPLOY_IOS.md` for day-to-day builds. Read that file first
for the one-time Apple Developer account setup; this file is what you
run afterward, every time you want to ship a build.

(`fastlane/README.md` in this folder is auto-generated by fastlane
itself and gets overwritten every run — this file won't be.)

Nothing here authenticates with your Apple ID + password/2FA. Every
lane uses an **App Store Connect API key** instead — that's what makes
this scriptable. The key, and the passphrase that protects the signing
certs, live in the **macOS Keychain**, never in this repo.

Every command is wrapped in `fastlane/keychain-env.sh`, which reads
those secrets out of the Keychain and puts them in the environment of
that one command. They never touch disk.

## One-time setup (do this once, on each Mac you'll ship from)

1. Install fastlane: `brew install fastlane` (this repo also has a
   `Gemfile`, so `bundle exec fastlane ...` works too if you prefer
   pinned versions — either is fine).
2. Create the Keychain items. All four live under the account
   `toto-asc`. The `-w` flag is omitted on purpose so `security`
   prompts for the value instead of putting it in your shell history:

   ```
   # App Store Connect API key ID (e.g. GY2PG9TC8Z)
   security add-generic-password -a toto-asc -s toto-asc-api-key-id -w

   # Issuer ID (the UUID from Users and Access → Integrations)
   security add-generic-password -a toto-asc -s toto-asc-issuer-id -w

   # The .p8 private key's full contents, BEGIN/END lines included
   security add-generic-password -a toto-asc -s toto-asc-api-key-p8 \
     -w "$(cat /path/to/AuthKey_XXXXXXXXXX.p8)"

   # The passphrase match uses for chintheman/toto-ios-certs.
   # If you haven't bootstrapped certs yet, skip this — step 4 creates it.
   security add-generic-password -a toto-asc -s toto-asc-match-password -w
   ```

   Delete the downloaded `.p8` afterwards; Apple only lets you download
   it once, and the Keychain copy is now the canonical one.
3. Sanity-check that the wiring works — this needs no signing, so it's
   safe to run anywhere:
   ```
   fastlane/keychain-env.sh bundle exec fastlane test
   ```
4. **Bootstrap signing certs (only ever needed once per Apple Developer
   account, not once per machine):** if `chintheman/toto-ios-certs` is
   still empty, run:
   ```
   fastlane/keychain-env.sh bundle exec fastlane certs_bootstrap
   ```
   `match` will prompt you to choose a passphrase the first time. Pick a
   strong random one, then store it as `toto-asc-match-password` (step 2)
   so later runs are non-interactive. This is the one step Apple requires
   an interactive login for. After this, every other machine just reads
   the encrypted certs.

## Everyday use

**Ship a new TestFlight build:**
```
fastlane/keychain-env.sh bundle exec fastlane beta
```
Bumps the build number, archives, uploads to TestFlight. Does **not**
submit for App Review — go test it on your phone via TestFlight first.

**Seed or refresh the local metadata files from what's actually live:**
```
fastlane/keychain-env.sh bundle exec fastlane pull_metadata
```

**Push edited App Store listing copy/screenshots** (no binary, no
submission):
```
fastlane/keychain-env.sh bundle exec fastlane metadata
```

**Submit the TestFlight build you already approved for App Review:**
```
fastlane/keychain-env.sh bundle exec fastlane release
```
`automatic_release` is deliberately off — once Apple approves, you
press "Release This Version" in App Store Connect yourself.

## Why this is safe to run unattended-ish

- No Apple ID/password/2FA anywhere in this flow — API key only.
- `match` runs `readonly: true` on every lane except `certs_bootstrap`,
  so a normal `beta` run can never silently regenerate/invalidate a
  cert another machine depends on.
- The certs repo (`toto-ios-certs`) is encrypted at rest — its GitHub
  privacy setting isn't actually the security boundary, the Keychain-
  held passphrase is.
- Nothing here auto-submits to App Review. `release` requires you to
  run it by hand, after you've personally tested the TestFlight build.

## Note on the Keychain and SSH

`security` can't read the login keychain from a non-interactive SSH
session while it's locked — you'll get "User interaction is not
allowed." Unlock it first:

```
security unlock-keychain ~/Library/Keychains/login.keychain-db
```

This is only a concern for remote/CI-style runs; a normal terminal on a
logged-in Mac already has it unlocked.
